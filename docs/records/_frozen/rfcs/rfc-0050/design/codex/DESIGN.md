# RFC 0050 Codex Design
author: designer-codex-gpt-5.5-001
status: draft
date: 2026-05-20

## Summary

Implement RFC 0050 by adding a native localhost HTTP MCP transport to
`striatumd` and narrowing `-agent-loop` to a PTY/bootstrap supervisor. The
transport should reuse `go/pkg/mcp.Service.ToolsList` and `ToolsCall` exactly
as the authority bridge: HTTP parsing and MCP framing live outside it, while
tool visibility, capability checks, daemon RPC dispatch, and audit rows remain
owned by the existing RPC server and authorizer path.

The agent loop should stop calling `work.await_packet`, stop writing packet
JSON to child stdin, and stop completing or releasing work on child exit. It
should launch the configured terminal agent in a PTY, inject a concise bootstrap
prompt containing the MCP endpoint, repository id, session id, and token
location, then let the agent act as an autonomous MCP client.

## HTTP Listener

Add an HTTP server to `go/cmd/striatumd` beside the existing Unix socket RPC
listener. It should be optional at first but enabled by default on loopback once
tests prove it stable.

Recommended configuration:

- `--mcp-http-addr` with default `127.0.0.1:0` for automatic port selection.
- `STRIATUM_DAEMON_MCP_HTTP_ADDR` as the environment override.
- The selected listener URL written to the daemon runtime directory as
  `mcp-http-endpoint` with mode `0600`, next to the existing runtime
  `client-token`, not under the target repository `.striatum/` scratch tree.
- `--mcp-http-addr=off` or an empty env value disables the transport for
  debugging and phased rollout.

The listener must refuse non-loopback TCP addresses unless a later product
decision explicitly accepts networked daemon MCP. `localhost`, `127.0.0.1`,
and `::1` are valid. Unix socket RPC remains the canonical CLI/admin transport;
the HTTP MCP listener is an agent-facing local tool transport, not a hosted
service.

TLS should be out of scope for V1. Loopback-only binding plus bearer capability
tokens matches the current local service posture. Adding self-signed TLS would
create client trust-store friction without improving the local threat model in
a meaningful way.

## Endpoint Shape And Framing

Expose:

- `GET /mcp/sse` for the MCP server-to-client event stream.
- `POST /mcp/messages?session_id=<id>` for client-to-server JSON-RPC messages
  bound to that SSE session.
- `GET /healthz` or `GET /mcp/healthz` for local readiness checks without
  exposing registry details.

This is the common HTTP/SSE MCP pattern: the SSE connection opens first, the
server sends an initial `endpoint` event naming the POST URL for that session,
and the client posts JSON-RPC requests to that URL. Each posted request gets a
single corresponding JSON-RPC response emitted on the SSE stream.

SSE event names:

- `endpoint` with `data: {"uri":"/mcp/messages?session_id=..."}`.
- `message` with a JSON-RPC response body for `initialize`, `tools/list`, and
  `tools/call`.
- `ping` every 15-30 seconds as keep-alive, using either SSE comments or a
  small event payload.
- `error` for transport/session errors that occur after the stream is open.

`tools/list` and `tools/call` should remain unary at the MCP layer. A single
tool call may long-poll internally, especially `work.await_packet`, but the MCP
transport should emit one response per request. Streaming partial tool-call
results would add correlation, ordering, and backpressure complexity without a
current Striatum method that needs partial output.

Each SSE session should have:

- A random session id generated by the daemon, not supplied by the client.
- A bounded outbound channel, for example 32 or 64 pending messages.
- A request body size cap no larger than the existing daemon RPC envelope cap
  unless a method-specific need justifies more.
- Cancellation tied to HTTP disconnect and daemon shutdown.

If the outbound channel fills, close the SSE session with a transport error and
let the agent reconnect. Do not buffer unboundedly for slow clients.

## Auth Path

Use bearer tokens:

```text
Authorization: Bearer <capability-token>
```

Accepting a `token` query parameter is useful for manual curl tests but should
not be the documented path because URLs leak into shell history, process
listings, browser histories, and logs. If query tokens are supported at all,
they should be rejected when an `Authorization` header is present and omitted
from every log line.

Token handling:

- The SSE `GET` authenticates only enough to create a session. If no token is
  present, the session may still open, but `tools/list` will return the visible
  set for an empty token and `tools/call` will fail closed through existing
  authorization.
- The POST endpoint accepts the bearer token on each request and passes it to
  `mcp.Service.ToolsList` or `ToolsCall`.
- The token is not stored in the SSE session state except, optionally, as a
  redacted "token present" boolean for diagnostics.
- Repository scope remains an argument-level concern. `tools/list` should pass
  `repository_id` from MCP params into `VisibleTools`; `tools/call` should pass
  arguments through to daemon RPC so ordinary repo-scope checks apply.

This keeps the real authorization boundary where it already is:
`rpc.Server.HandleWithoutHandshake` re-authorizes every `tools/call`, and
denials still produce daemon audit rows with `transport = "mcp"`.

## Tools Mapping

Create a small Go HTTP MCP transport package, for example `go/pkg/mcphttp`, that
depends on `go/pkg/mcp` but does not duplicate tool policy.

Mapping:

- `initialize` returns MCP protocol/server metadata and capabilities for tools.
- `tools/list` calls `mcp.Service.ToolsList(ctx, params, token)`.
- `tools/call` extracts `name` and `arguments`, generates a request id when the
  client does not provide one, and calls
  `mcp.Service.ToolsCall(ctx, name, arguments, token, requestID)`.
- Unknown MCP methods return JSON-RPC `-32601`; unknown Striatum tool names
  still flow through `ToolsCall` and return structured `method_unknown`.

The result from `ToolsCall` already contains:

- `structuredContent.ok`
- `structuredContent.method`
- `structuredContent.data`
- `structuredContent.error`
- `structuredContent.error_message`
- `isError`

Keep that shape. For `capability_denied`, `token_expired`, `repo_not_registered`,
and `method_unknown`, the MCP response should be a successful JSON-RPC response
whose tool result has `isError: true`, matching MCP tool-call conventions.
Malformed MCP JSON, missing `name`, non-object `arguments`, invalid session id,
and oversized request bodies are transport or JSON-RPC errors.

## Agentloop PTY Bootstrap

Change `go/pkg/agentloop.Run` from a polling wrapper into a PTY supervisor:

1. Resolve the MCP endpoint from `STRIATUM_DAEMON_MCP_HTTP_URL`, the daemon
   runtime `mcp-http-endpoint` file, or a new `--mcp-http-url` flag passed by
   `striatumd -agent-loop`.
2. Read the capability token from the daemon runtime `client-token` when
   available, falling back only to the existing repo-local capability-token
   compatibility file while that cache still exists.
3. Spawn the configured command in a PTY with the target repo as cwd.
4. Write a bootstrap prompt to the PTY master.
5. Wait for process exit and return that exit status without mutating workflow
   state.

Bootstrap prompt shape:

```text
You are a Striatum lane agent for session sess_... in repository repo_... .
Use the local Striatum MCP server at http://127.0.0.1:<port>/mcp/sse .
Authenticate with the bearer token from <runtime-token-path>; do not print it.
Call tools/list first, then call work.await_packet with repository_id,
session_id, and an appropriate lease_seconds value. Acknowledge and complete
work using the commands in each packet or the matching MCP tools. Treat
.striatum/ as operational scratch only and publish only curated artifacts.
```

If the target agent CLI supports MCP server configuration via environment
variables or command flags, the agent loop may set those too. The prompt is
still required as a portable fallback and as visible operator context.

The agent loop must not infer job success from child exit. A terminal agent can
exit after publishing a blocker, after no work is available, or after a tool
failure. Workflow state must advance only through daemon methods called by the
agent.

## Alternatives Considered

### Keep The Existing Stdin Proxy

The current `agentloop` implementation calls `work.await_packet`, writes raw
packet JSON to the child, and then calls `work.complete` or `work.release`
based on the child exit code. This is easy to test but violates RFC 0050's main
goal: the agent is no longer an autonomous MCP client, and the wrapper becomes
an unreviewed workflow actor that mutates state on behalf of the agent.

### Spawn A Stdio MCP Server Per Agent

The old Python `src/striatum/mcp.py` shape and a possible Go replacement both
fit standard stdio MCP clients, but they add process management and duplicate
daemon connection setup even though `striatumd` is already resident. This also
keeps the product dependent on wrapper lifecycle bugs and delays deletion of
the Python MCP path.

### Single POST-Only HTTP JSON-RPC

A pure `POST /mcp` endpoint would be simpler than SSE and enough for unary tool
calls, but it would not match the accepted RFC direction and would leave agents
that expect HTTP/SSE MCP unable to connect naturally. The SSE session also gives
Striatum a future-compatible place for server-initiated notifications without
introducing WebSockets.

## Risks And Unknowns

- Slow clients can block memory if the SSE implementation queues without bound.
  Use bounded channels, write deadlines where possible, and explicit session
  close on backpressure.
- Automatic port selection avoids collisions but requires a discoverable
  endpoint file. Fixed ports are easier to document but fragile across multiple
  daemon instances and test runs.
- Bearer tokens in bootstrap text can leak into terminal scrollback. Prefer
  token file paths or environment variable names in the prompt; never echo the
  token value.
- Query-string tokens are convenient and dangerous. Header-only should be the
  documented path.
- Existing Unix socket RPC behavior must not regress. The HTTP server should
  share `rpc.Server` but be started and shut down independently.
- Request id de-duplication in `rpc.Server` is daemon-wide. The MCP transport
  must generate unique request ids for tool calls when clients omit them or use
  short ids that could collide with Unix-socket clients.
- The MCP HTTP/SSE dialect needs one concrete compatibility target. Before
  broad rollout, verify with at least one real MCP client, not only curl and
  unit tests.

## Rollout Sketch

1. Add `go/pkg/mcphttp` with unit tests for `initialize`, `tools/list`,
   `tools/call`, unknown method, denied capability, keep-alive, and slow-client
   channel overflow. Use a fake `mcp.Service` or fake `rpc.Server` where
   possible.
2. Wire the HTTP listener into `go/cmd/striatumd` with loopback validation,
   `--mcp-http-addr`, env override, endpoint-file publication, and graceful
   shutdown alongside the Unix socket listener.
3. Add an integration test that starts the Go daemon, connects to `/mcp/sse`,
   posts `tools/list`, and calls a read-shaped method through `tools/call`,
   asserting the daemon audit path records transport `mcp`.
4. Refactor `go/pkg/agentloop` into a PTY/bootstrap supervisor and remove its
   direct use of `work.await_packet`, `work.complete`, and `work.release`.
5. Run a supervised lane smoke where the agent calls `work.await_packet` via
   MCP and completes a minimal work packet.
6. Delete `src/striatum/mcp.py` and update `docs/MCP.md`, skills/templates, and
   tests that still describe the Python stdio wrapper as available.

Defer richer server notifications, TLS, non-loopback serving, and automatic
per-agent token minting to later RFCs. The V1 implementation should prove the
transport, preserve capability-gated daemon authority, and remove the proxy
wrapper behavior without expanding Striatum's product boundary.
