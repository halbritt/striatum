## Executive Summary

The "Operator Bypass" is a fundamental trust-boundary failure where the entity responsible for **routing** work (the AI Operator) also possesses the **capability** to author that work natively. To achieve **Absolute Provenance**, we must move from a model of *trusting the operator's shell* to *verifying the state transition*.

This analysis proposes three advanced strategies to close the "Provenance Loophole":
1.  **Model-Rooted Token Attestation (MRTA)**: Utilizing provider-side cryptographic signatures to verify that bytes were generated by a specific model instance, not the operator harness.
2.  **Deterministic Application (D-Apply)**: Stripping the Operator of `git-write` authority and moving it to a trusted local supervisor that only applies patches backed by a quorum of attested verdicts.
3.  **Semantic Entropy Analysis (SEA)**: Detecting "Idea Laundering" (where an operator dictates specific code to a lane) by measuring the statistical information-gain between an intent-prompt and its resulting patch.

---

## 1. The Core Dissonance: Routing vs. Authoring

In the current Striatum architecture, the **Operator** is a privileged user. It has the keys to the kingdom (the repo) and a set of instructions to "behave" and use the workflow. This is **Advisory Security**.

True Provenance requires **Functional Isolation**. We must treat the Operator as an **Untrusted Planner**. It can suggest a path, but it cannot move the cursor.

### The Provenance Hierarchy
*   **Layer 0 (Current):** Cooperative provenance (Advisory).
*   **Layer 1:** Byte provenance (Did a lane process write these files?).
*   **Layer 2:** Intent provenance (Was this change decided by a peer-review quorum?).
*   **Layer 3:** Model provenance (Was this code generated by the claimed LLM?).

The Loophole exists because Layer 0 is the only hard gate. An AI Operator can satisfy Layer 0 (it calls the plugin) while bypassing the *spirit* of Layers 1 and 2 by ghost-writing the code natively.

## 2. Advanced Mitigation Strategies

### Strategy A: Model-Rooted Token Attestation (MRTA)

**Concept:** Shift the trust anchor from the *local process* to the *remote provider*.

**Mechanism:**
1.  **Provider-Signed Responses:** Future frontier model APIs (e.g., Google Vertex AI, Azure OpenAI) provide a cryptographic signature for every response. This signature covers the `(model_id, prompt_hash, response_text, timestamp, request_id)`.
2.  **Lane Verification:** When a Striatum lane (e.g., an implementer) receives a response from the provider, it requests a signed attestation.
3.  **Artifact Binding:** The `publish-artifact` command is extended to include this `provider_signature`.
4.  **The Verifier:** The local Striatum runner verifies the signature against the provider's public key.

**Why this works:** Even if the Operator tries to ghost-write code and "fake" a lane's success, it cannot produce a valid signature from the *lane's* provider account/identity for the *lane's* specific task prompt without actually running the model. This makes "Byte Provenance" cryptographically hard.

**Limitation:** Depends on model providers exposing these signing APIs (part of the "Responsible AI" roadmaps at major labs).

### Strategy B: Deterministic Application (D-Apply)

**Concept:** The Repository is a "Sealed Box." The only way in is through a "Trusted Applier."

**Mechanism:**
1.  **Read-Only Operator:** The Operator's harness (Gemini CLI, etc.) is launched with **read-only** access to the source code (using mount namespaces or `bwrap`).
2.  **Patch Escrow:** Lanes do not write to the repository. They write to an ephemeral, isolated scratch space. Striatum captures the delta as a **Patch Artifact**.
3.  **The Apply Job:** A specific workflow job of type `apply` is the **only** process with write-access to the repo.
4.  **Quorum Gate:** The `apply` job is deterministic. It only executes if:
    *   The `author` job (lane) produced an attested patch.
    *   `N` `review` jobs (lanes) recorded `accept` verdicts for the **exact hash** of that patch.
    *   The `operator` (human or AI) has authorized the transition via a `decision` artifact.

**Why this works:** The Operator *cannot* bypass the workflow because it literally lacks the system permissions to touch a `.py` file. It is forced to be a high-level manager, delegating authorship to the lanes that *do* have scoped write access.

### Strategy C: Semantic Entropy Analysis (SEA)

**Concept:** Detect "Idea Laundering" by measuring "Surprise."

**Mechanism:**
1.  **The Information Gap:** In a healthy workflow, a **Task Prompt** (High Entropy/Intent) results in a **Code Patch** (Low Entropy/Implementation). The lane *generates* information by translating intent into syntax.
2.  **Dictation Detection:** If an Operator dictates the fix to the lane (e.g., "Change line 50 to `return x`"), the Information Gap is near zero. The lane's output is almost entirely predictable from the prompt.
3.  **Surprise Metric:** Striatum runs a "Verification Model" (a smaller, cheaper LLM) that calculates the `log-probability` of the patch given the prompt.
4.  **The Firewall:** If the patch's probability is too high (meaning the prompt essentially contained the patch), the artifact is flagged as **"Collusive"** or **"Dictated."**

**Why this works:** It addresses the "Intent Loophole." Even if the bytes are clean (Byte Provenance), SEA ensures the *creative decision* was made by the lane, not the operator. It forces the operator to provide *intent*, not *code*.

## 3. The "Sealed-Run" Protocol (Proposed Implementation)

To combine these into a single shippable feature, we propose **Sealed-Run Mode**:

1.  **Isolation:** `striatum run start --sealed` launches the operator in a `bwrap` container with read-only source.
2.  **Ephemeral Lanes:** Every job claim spawns a fresh, attested supervisor (RFC 0009).
3.  **Hash-Locked Reviews:** Verdicts must match the SHA256 of the patch artifact.
4.  **Autonomous Apply:** Once the graph is satisfied, the runner (not the operator) applies the patch and commits it using a runner-specific GPG key.

## 4. Conclusion: From Guidance to Governance

The current state of AI orchestration is "Guidance": we tell the AI how to behave. Absolute Provenance requires "Governance": we build a system where the AI **cannot** behave otherwise.

By moving the trust boundary to **State Transitions** (D-Apply) and **Model Attestation** (MRTA), and auditing the **Information Gap** (SEA), we can turn Striatum from a bookkeeping tool into a hard provenance engine. This is the prerequisite for "Zero-Human" autonomous coding.
