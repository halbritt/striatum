# Ubiquitous Language

Status: draft
Date: 2026-05-06

This document defines the shared vocabulary for `striatum`. Terms should be
updated when decisions sharpen the product model or the implementation exposes
new operator-facing behavior.

`striatum` is generic local terminal-agent orchestration. Engram is the
incubation repository and the first reference *augmentation consumer* of
`striatum corpus export` bundles; it is not the product boundary and not a
runtime dependency. The augmentation contract is the bundle, not a client
library import — see [`docs/reference/spec.md` § Corpus Export And Augmentation
Boundary](spec.md) and [RFC 0057](../rfcs/0057-corpus-contract-v2.md).

## Core Terms

| Term | Definition |
|------|------------|
| agent | A terminal-based AI coding process launched or supervised by `striatum`, such as Claude Code, Codex, agy (Antigravity), or another configured model/runtime command. |
| agent lane | A named, portable launch configuration for an agent, including command template, adapter, capabilities, and optional default role. Lanes are configuration, not product identity. |
| lane selection | The workflow-authoring choice of which lanes exist and which jobs bind to them. Lane selection controls model/tool routing, review independence, supervision, worktree isolation, and adapter constraints; it is explicit workflow configuration, not an inferred default. |
| agent identity | The registered identity of an agent session, including session id, role, lane, capabilities, run id, and optional human-readable name. |
| agent slug | A human-readable session name, recommended as `<role>-<lane>-<ordinal>`, used for tmux windows, dashboards, logs, and prompts. It is not the database primary key. |
| adapter | Code that connects `striatum` to an external execution or interaction surface, such as tmux, a subprocess, Slack, or a model CLI. |
| adapter boundary | The line between core scheduling semantics and provider-specific execution details. V1 records lane commands and constraints, but core scheduling does not parse terminal output or infer behavior from provider names. |
| binary | The `striatum` executable that agents and humans invoke to read or mutate orchestration state. Per D094 / RFC 0043 it is the only client of the daemon, which is the single writer for all live workflow state. |
| repo-local control plane | The deterministic local control layer that stores and mutates workflow state for one target repository. Per D094 / RFC 0043 this is the `striatum` CLI plus the daemon-owned PostgreSQL instance under a `repository_id` scope; `.striatum/` next to each target repo is operational scratch only. |
| target repository | The repository/workspace being orchestrated by a run. It may be Engram during incubation, but the term is generic and should be used instead of assuming Engram. |
| incubation repository | The repository where `striatum` temporarily lives before standalone extraction. Today this is Engram; core product logic should not depend on that. |
| reference fixture | A checked-in workflow or scenario used to validate the runner. Fixtures may come from Engram, but they are examples of generic orchestration behavior. |
| live state | Authoritative mutable run state used by the control plane. Per D094 / RFC 0043 live state lives in the daemon-owned PostgreSQL instance under a `repository_id` scope, not in marker files, terminal panes, or committed reports. |
| durable provenance | Repository artifacts that make the run auditable after the live state is gone or ignored. Provenance can describe the run but is not the live message bus. |
| artifact | A durable output that should be reviewable after the live run ends, often stored in the target repository. Examples: findings, syntheses, prompt drafts, marker summaries, PRDs, specs, decision logs, and redacted evidence exports. |
| artifact author identity | Stable authorship metadata for a job or artifact: role id, lane id, declared model display name, and workflow job id. It is used instead of free-text workflow job titles in evidence exports, not as the visible artifact byline. |
| artifact title block | The human-readable top matter of a durable artifact. It may include title, date, status, target, verdict, and author metadata, depending on artifact kind. |
| artifact author | The privacy-safe reader-facing byline inside a durable artifact title block. Current convention is `author: <role-name>-<model-name>-<ordinal>`, for example `author: reviewer-codex-gpt-5.5-001`. It is for readers, not database identity, and intentionally excludes workflow job titles. |
| author line | A Markdown artifact title-block line derived from publish-time authorship truth. Lane-attested sessions use `author: <role-name>-<model-name>-<ordinal>`; unattested sessions use `author: operator` or, when registered with `--operator-label <label>`, `author: operator-self-declared-<label>`. |
| lane-liveness attestation | A derived value object for a session at a point in time. A session is attested only when it has an attached runner-owned supervisor row for the same run/session, the pid is still the same process identity captured at launch, and the supervisor command matches the session lane command from the workflow snapshot. It proves a lane process binding is alive; it does not prove artifact bytes came from model output. |
| lane-bound | A primitive, rows-only property of a supervised session: the attached supervisor row, its supervisor pointer, and the daemon-supervisor row all exist in the attached state for the same run/session and agree on the pid identity captured at launch. Computed purely from daemon-DB rows, never from a live process probe. It is necessary but not sufficient for lane-liveness attestation — a session can be bound yet not alive once the bound process has exited. |
| lane health | The composite derived value object for a supervised session at a point in time, computed in one place from the lane's daemon-DB rows plus a single process/pane liveness probe. It exposes orthogonal axes behind one interface — lane-bound (rows only), alive (probe), lane-liveness attestation (bound and alive and start-token-verified), delivery liveness, and stall class — so the attestation rules are defined once rather than recomputed across the mutation and read paths. |
| delivery liveness | A derived value object for whether the runner-owned delivery path can still accept new packets for a supervised lane. It is distinct from pane or PID liveness: a tmux pane can be alive and lane-attested while delivery is degraded because the helper-owned attach bridge exited. |
| lane backend | The read-surface badge for the supervisor transport backing a lane: `tmux`, `plain_pty_fallback`, or `plain_pty`. It is distinct from pane liveness and delivery liveness. |
| operator byline | The artifact author line used when a session is not lane-attested: `author: operator`, optionally `author: operator-self-declared-<label>`. The label is deliberately operator-asserted, tightly validated, YAML-safe in front matter, and never equivalent to a lane/model byline. |
| provenance mode | A workflow-level label for the guarantee level Striatum is allowed to claim. `advisory` records local workflow evidence without source containment; `attested_bylines` adds lane-liveness byline derivation/gates without source containment; `sealed_patch` is reserved for daemon-mediated sealed apply and refuses direct repo-local startup without hard local containment/apply authority. |
| artifact publisher | The component that validates and records selected job outputs as durable repository artifacts. It checks lease ownership, write scope, path safety, artifact kind, file existence, and content hash. |
| artifact front matter | An optional YAML `---`-delimited block at the top of a durable Markdown artifact carrying machine-checkable metadata. The older `key: <json-value>` style remains valid, and schemas may declare nested mappings or list rows when the contract needs them. The publisher records artifacts but never rewrites them. |
| front-matter schema | A registered per-kind schema for `artifact front matter`. V1 defines schemas for durable decision/review artifacts (`decision`, `finding`, `findings_ledger`, `synthesis`, `support_ledger`, `action_item_ledger`, `harness_improvement_proposal`, `escalation`, `collaboration_ledger`) plus operator/provenance artifacts (`operator_brief`, `work_plan`, `progress_note`, `operator_report`, `commit_request`, `pr_request`, `auto_finalize_gate_evidence`, `claim_ledger`, `receipt`) and panel/barrier provenance artifacts (`join_manifest`, `advisory_minority_report`). When a file with a front-matter block is published under a kind that has a registered schema, validation runs and rejects invalid metadata; files without a front-matter block remain accepted except for `collaboration_ledger`, where the block is required because the verdict gate reads it. |
| support ledger | A curated, redaction-safe Markdown artifact (kind `support_ledger`, RFC 0003) that maps each claim in another artifact to the supporting evidence: file paths, command summaries, hashes, or referenced reports. Used to make later evidence audits inspect concrete artifacts rather than the producing agent's prose. |
| evidence audit | A workflow convention (RFC 0003) where a downstream review-only job reads a produced artifact, its `support ledger`, and the referenced evidence files, then emits a `finding` artifact with verdicts for ledger rows. "Evidence audit" is a workflow naming convention, not a new `job_type`; underlying job types remain `review`. |
| action-item ledger | A Markdown artifact (kind `action_item_ledger`, RFC 0004) that normalizes review feedback into stable action ids, each with a source review artifact, requested change, owner, resolution status (`resolved`, `resolved_with_modification`, `deferred`, `rejected`, `blocked`), and resolution evidence. Lets re-review jobs verify resolution directly instead of relying on prose handoffs. |
| collaboration ledger | A Markdown artifact (kind `collaboration_ledger`, RFC 0093) emitted by an adjudicator to record structured live-dialogue evidence: claims, challenges, rebuttals, constraints, nominations, dialogue refs, and the gate verdict. It references RFC 0081 dialogue turns instead of copying transcripts or terminal output. The additive `v1.1` schema carries the RFC 0094 §5 adjudicator-reliability extras: per-`challenge` `correspondence` (Check-B), per-entry `coverage` (fog-of-war), and the top-level `adjudicators[]` / `adjudication_mode`. |
| harness improvement proposal | A Markdown artifact (kind `harness_improvement_proposal`, RFC 0005) emitted by an advisory meta-analysis job. It documents observed runner friction, a proposed change to a `target` (`prompt`, `workflow`, `spec`, `defaults`, or `documentation`), expected benefit, and optional risk and rollback fields. The runner never auto-applies these proposals; reviewer and operator disposition still gate any harness change. |
| escalation artifact | A Markdown artifact (kind `escalation`, RFC 0053) emitted by the AI operator when the work is stuck and needs human-principal judgment. Its V1 front matter carries blocker-shaped metadata (`run_id`, optional `job_id` / `session_id`, `severity`, bounded `blocker_kind`, `description`) plus required `reasoning` and `requested_action`. It is durable provenance for the principal inbox; it does not create a dedicated live-state table. |
| evidence export | A redacted Markdown repository artifact generated from live runner state so a run can be audited from a fresh checkout without committing `.striatum/` scratch or exposing daemon DB live state. |
| redaction | The act of replacing free-text fields that may contain user or agent prose, such as blocker descriptions and verdict rationales, before publishing an evidence export. |
| coordinator | The control role for a workflow. In the hybrid model, the deterministic coordinator owns state and gates, while one selected model lane may act as the AI coordinator for conversational project management. |
| deterministic coordinator | The non-AI control plane that owns workflow state, gates, process launch, retries, stop conditions, message routing, write-scope checks, and durable state updates. |
| AI coordinator | A model lane registered as a `coordinator`-role session inside a running workflow (declared at `workflow.coordinator.{role_id, lane_id}`). Designed to claim a `coordinator`-typed job and act as a project manager: goal tracking, blocker triage, next-action selection, human-checkpoint escalation, summarization, dispatching downstream jobs through `striatum` commands. It does not synthesize major artifacts unless assigned a synthesis job. **Status as of v1.1.0: declared in every dogfood workflow but never actually claimed in any run** — the workflow vocabulary supports it (D004/D005), but no production workflow has yet exercised the coordinator-as-claimed-session path. The role is currently filled by the `operator` (see below). |
| operator | The entity *outside* the workflow that runs `striatum` CLI verbs against a target repository (daemon-mediated per RFC 0043). The operator is the keyboard. In current practice the operator is a coding-agent CLI (Claude Code, Codex, agy) loaded with the RFC 0015 skill bundle, and `docs/how-to/how-to-agent.md` is the load-bearing playbook. Operators register sessions (researcher / designer / reviewer / implementer / etc.), claim work, publish artifacts, and complete jobs. The `human principal` (below) is a distinct, escalation-only role; a human at the keyboard outside of an escalation is acting as the operator with the same CLI surface as an agent CLI. |
| human principal | The authority figure outside the workflow whose role is to resolve unresolvable blockers or decisions (RFC 0053 / D103). The principal is bounded by *function*, not by *interface*: same CLI surface as the AI operator, but role-scoped to escalation resolution — never routine claim / ack / publish / verdict / complete. Escalation triggers are a closed set of declared blocker classes (`ambiguous_goal`, `missing_authority`, `contradicting_decisions`, `no_available_reviewer_lane`, `committee_stalemate`, `override_required`) plus AI-self-declared `escalation` artifacts. The principal resolves via `striatum decision record` or (deferred) a dedicated `escalation resolve` verb. Reachable async; this role does not imply paging / SLAs. |
| operator surrogate | **Historical term, retained only to interpret older docs.** Originally defined when the `operator` was assumed to be human and an LLM agent calling CLI verbs was modelled as the human's "hand on the keyboard," with authority delegated by the human. In current practice the operator is species-agnostic — the agent CLI *is* the operator, not a stand-in for one — and no human principal is presumed. The real distinction the term tried to draw (outside-the-workflow operator vs. inside-the-workflow `coordinator` session) lives directly under `operator` vs. `AI coordinator` now. |
| next action | A deterministic coordinator suggestion returned by status or introspection commands, such as resolving a human checkpoint, inspecting a blocker, claiming available work, or exporting run evidence. |
| coordinator skill | A deterministic, invocable coordinator capability exposed through chat and backed by `striatum` commands, such as resolving a prompt artifact, assembling a work packet, or dispatching a job. |
| synthesis job | A workflow job that combines findings, reviews, or intermediate artifacts into a new durable artifact. It is intentionally separate from the AI coordinator role to avoid attention dilution. |
| workflow | A configured graph of jobs, dependencies, gates, allowed write scopes, agent lanes, expected artifacts, and stop conditions. |
| workflow config | The user-authored JSON file that defines a workflow. V1 requires `striatum.workflow.v1` JSON and rejects YAML. |
| workflow type | A documentation and product-planning category that helps an operator choose a graph shape before editing `workflow.json`, such as minimal bounded job, review and synthesis, code change with bounded revision, human checkpoint, evidence-backed artifact, multi-review synthesis, or live collaboration substance gate. It is not a workflow schema field. |
| workflow shape | The generator's graph-family choice, such as `minimal`, `review`, `code_change`, `human_checkpoint`, `evidence_backed`, `implementation_panel`, `multi_review_synthesis`, `multi_phase`, `falsification_gate`, `cross_examination`, `adjudicated_constraint_extraction`, `divergent_ideation`, `fog_of_war_review`, `synaptic_prune`, or `custom`. It compiles to ordinary workflow jobs, edges, cycles, and optional phases; it is not a persisted workflow schema field. |
| divergent ideation shape | The RFC 0087 generator shape that widens a design space before narrowing it: parallel diverge branches (one cognitive frame each, fresh-session isolated) fan into a convergence critic that scores/clusters/trap-detects, then deepens the top survivors and synthesizes. The striatum-native, provenance-backed, provider-portable port of the ADHD method (`UditAkhourii/adhd`, MIT) — model calls live in lanes, never in a state transition. |
| cognitive frame | A vantage operator the divergent ideation shape binds to a diverge branch: a short id plus a one-line vantage that distorts how the problem is re-asked. Frames are an authoring input (RFC 0074 pack kin), not a persisted schema field. RFC 0129 gives each a `frame_kind` (`persona`/`operation`), a `category` (`persona`/`operation`/`temporal_forensic`/`risk_pricing`), and distortion-axis `dimensions`. |
| distortion axis | A named dimension on a cognitive frame (e.g. `time_anchor`, `agency`, `axis`, `operates_on`) the selector compares for anti-redundancy: two frames sharing two or more dimension values induce the same distortion and are refused in one run, keeping a run's branches structurally distinct (RFC 0129). |
| workflow template catalog | The bundled local package-data catalog that promotes selected workflow shapes, lane sets, role packs, and adversary packs into named templates with metadata and graph previews. It is exposed through `workflow templates list/show/render-md` and service read endpoints; V1 does not fetch remote templates or load target-repository extensions. |
| collaboration shape | An RFC 0093 workflow shape family for structured collaboration gates. V1 includes generated `falsification_gate` and `cross_examination` shapes as static challenge/rebuttal gates over published artifacts; both compose phase gates and a `collaboration_ledger` artifact without adding daemon methods. The family also includes the RFC 0098 `adjudicated_constraint_extraction` (`supported`) and the RFC 0094 `fog_of_war_review` / `synaptic_prune` shapes (`experimental`). |
| fog_of_war_review shape | The RFC 0094 §3 collaboration shape (`experimental`): the coordinator partitions the spec into disjoint fragments — one per interrogable reconstructor lane — while a judge alone holds the full spec; reconstructors interrogate peers to recover the constraints their fragment omitted; a coverage gate (the judge, scoring reconstructed / hallucinated / missed against ground truth) publishes a `collaboration_ledger` (shape `fog_of_war_review`); and the `proposal`-typed job is withheld behind that verdict via work-packet type sequencing. It is the mirror of `divergent_ideation`'s enforced isolation — deliberately partial context reconstructed through dialog. |
| synaptic_prune shape | The RFC 0094 §4 collaboration shape (`experimental`): after a forum closes, a `post_dialog_hook` emits a prune packet before the participant lanes' preserved-context window releases; each still-live participant nominates one claim to retire (with rationale); and the adjudicator records every claim nominated by ≥2 participants as a `nomination`-kind entry in a `collaboration_ledger` (shape `synaptic_prune`) — the durable negative preamble injected into future runs on the same topic. A dead target is recorded, not hung on. |
| negative preamble | The RFC 0094 §4 durable, topic-scoped `collaboration_ledger` of claims `synaptic_prune` retired (≥2-vote nominations). It is injected as a "do not re-litigate: …" authoring preamble into a later run that explicitly opts into the prior topic — provenance, not a reputation score or economy. Injection is via the existing pack/prepare authoring-context path; there is no cross-run automatic linkage. |
| substance gate | The RFC 0093 phase-gate convention where a downstream commit/publication job becomes reachable only after an adjudicator publishes a structured `collaboration_ledger` verdict. It is implemented with ordinary `phase_synthesis` and cycle routing. |
| adjudicator | A workflow role that reads the curated `dialogue` trajectory and published artifacts, then emits a `collaboration_ledger` verdict. The adjudicator is reviewer-independent by policy and must not use raw PTY logs or provider stdout/stderr as evidence. |
| Check-B | The RFC 0094 §5 semantic challenge↔rebuttal rubric that raises the substance-gate anti-theater bar above V1's structural presence check. The adjudicator records, on each `challenge` entry of a `collaboration_ledger`, a `correspondence` judgment — `landed_and_rebutted`, `landed_unrebutted`, or `not_material` — of whether the rebuttal materially addressed the specific gap the challenge raised. Once any `correspondence` is recorded (Check-B engaged), a clearing verdict requires at least one `landed_and_rebutted` and no `landed_unrebutted`; the publisher refuses otherwise (exit 6). A confident non-rebuttal that cites the right turn ids is recorded `landed_unrebutted` and can no longer talk the gate past. |
| second adjudicator | The RFC 0094 §5 / RFC 0064 opt-in reliability gate for high-stakes substance gates. A `collaboration_ledger`'s `adjudication_mode: second_on_disagreement` requires a **clearing** verdict to be backed by at least two **distinct** adjudicator session ids in `adjudicators[]` (a second, distinct lane/model independently scored the same trajectory and agreed). A contested clear is conservatively recorded as `needs_revision` (which does not require the second adjudicator). `single` (or an absent mode) leaves the single-adjudicator gate unchanged. |
| lane set | The generator's lane-topology choice, such as `local`, `single_agent`, `author_reviewer`, `multi_review`, or `custom`. It is separate from shape so the same graph can run on different lane topologies. |
| role pack | A generator/catalog authoring input that names a reusable set of workflow roles for a shape. It is not live runner state; generated workflows persist only normal `roles` and job `role_id` bindings. |
| adversary pack | A generator/catalog authoring input that names skeptical review dimensions or postures for a shape. It is not live runner state; generated workflows persist normal review jobs and review postures. |
| workflow generation spec | A JSON-serializable input object with schema version `striatum.workflow_generator.v1` that selects shape, lane set, artifact root, scaffold root, branch suggestion, lane commands, modifiers, and options. It is an authoring input, not live run state. |
| generated workflow | The output envelope from `generate_workflow`: a validated `workflow.json` object, generated file contents, graph metadata, warnings, and validation status. Only the written workflow tree becomes durable repository material. |
| custom plan | A constrained generator plan for `shape: "custom"` using the closed block vocabulary (`draft`, `review`, `synthesis`, `implementation`, `test`, `human_checkpoint`, `support_ledger`, `evidence_audit`, `final_review`). It exists to avoid raw JSON freestyle while still allowing non-built-in graph shapes. |
| workflow cycle | An explicit bounded loop in a workflow graph, such as revision -> re-review -> proceed/stop. Unbounded autonomous cycles are out of scope for v1. |
| interrogation target | An upstream workflow job marked `interrogable: true` whose completing session stays available for preserved-context questioning until its direct and explicit interrogation consumers are terminal. The live target is a session window, not an artifact transcript. |
| interrogation consumer | A workflow job that may interrogate an upstream `interrogation target`. Consumers are either direct dependents in the job graph or jobs that declare the target in `interrogation_targets`. |
| explicit interrogation consumer | A workflow job that declares `interrogation_targets` to consume an upstream target's live preserved context without adding a scheduling dependency edge. The relationship is resolved from the frozen workflow snapshot and live job rows; it is not a materialized table or fake graph edge. |
| post_dialog_hook | An optional declaration on an RFC 0086 conversation (`post_dialog_hook: {deliver_to, packet_type}`, `deliver_to` a participant/coordinator session id). On conversation close — explicit or auto-close at `max_rounds` — the daemon emits exactly one work packet to `deliver_to`, carrying the participant session ids plus a transcript reference (the conversation id; the curated transcript is read via `conversation.show`, never raw provider output), inside the close transaction so the emit lands before any participant teardown (emit-before-teardown). It reuses the existing `queue_messages` delivery path (a `post_dialog_hook` agent message the coordinator's await loop delivers) and adds no new daemon method or owner-held job, so a coordinator can fan out follow-up work (for example synaptic_prune nominations) while the participants are still live. RFC 0095 Phase 3 reuses the same "keep participants live through a gate" mechanism for review panels. |
| work-packet type sequencing | A generator-authoring capability (RFC 0094 §2): a phase may declare `gate: {withhold_packet_types: [<type>...], until_verdict_clears: <gate_job_id>}` so jobs of a withheld work-packet type are unreachable until a named verdict job clears. It compiles to ordinary cross-phase dependency edges (every withheld-type job depends on the gate job's clearing verdict, exactly as a commit phase depends on a review verdict) — `workflow validate` rejects a gate whose gate job is missing, is not a verdict-emitting type, or whose withheld-type jobs lack the dependency edge, and `workflow lint` surfaces the sequencing. The daemon withholds the jobs through the dependency it already enforces; no new RPC method or route is added. |
| workflow snapshot | The immutable JSON workflow body and hash loaded into daemon-owned PostgreSQL under the run's `repository_id` scope, so later file edits do not silently change the run contract. |
| workflow fixture | A checked-in example workflow used to validate orchestration behavior without live model calls. |
| review revision policy | Workflow configuration that states how root-review `needs_revision` verdicts are routed, for example to a human checkpoint or to declared revision cycles. |
| shared resource | A workflow job's declared mutable external fixture, such as a test database or hardware device, named in `shared_resources`. Work packets expose it under `context.shared_resources`; `workflow validate --json` reports warnings when parallel jobs share an exclusive resource or reuse a per-lane namespace. V1 surfaces coordination hazards but does not acquire daemon-owned locks for external resources. |
| reviewer access scope | The optional `reviewer_access_scope` workflow field on a review job (RFC 0002). One of `document_only` (read only the target documents in `inputs`), `artifact_augmented` (also read supporting artifacts/reports/ledgers in `inputs`), or `repo_level` (inspect the repository within the job's declared `write_scope`). The work packet exposes the value in a `review_policy` block. |
| reviewer context policy | The optional `reviewer_context_policy` workflow field on a review job (RFC 0002). One of `fresh` (require a brand-new role/session and avoid prior thread state) or `cross_round` (retain context to verify earlier issues were resolved). Setting it to `fresh` silently implies `fresh_session_required: true`; explicitly combining `fresh` with `fresh_session_required: false` is rejected. |
| fresh-context review | A review job whose `reviewer_context_policy` is `fresh`. The reviewer must be instantiated as a new role/session and must not rely on prior round state when forming a verdict. |
| review posture | The optional `review_posture` workflow field on a review job (RFC 0018). One of nine first-class values (`neutral | devils_advocate | security | threat_model | latency_performance | ergonomics_dx | accessibility | compliance_license | supply_chain`) or a `custom:<name>` value for off-list adversarial flavors. The runner exposes the value on the work packet's `review_policy.posture` and appends a deterministic posture-specific instruction sentence to `review_policy.instruction` for first-class postures. Custom postures get no auto-appended sentence. |
| required review postures | The optional `required_review_postures` workflow field on a build job (RFC 0018). A non-empty list whose entries each name a `review posture` (first-class or `custom:<name>`). The workflow validator refuses (exit code 8) when any required posture is not the `review_posture` of a review job reachable from the build via the directed edge graph in either direction. Runtime enforcement is preserved by the existing edge-verdict gate plus run-completion semantics; no separate runtime gate is added. |
| scaffold layout | A historical term for optional filesystem layout generation. Current Go builds do not expose the retired `init --with-ddd-layout` or `init --with-striatum-layout` flags; use `workflow generate --scaffold-root ... --artifact-root ...` for current workflow trees. |
| scaffold status | The per-target outcome reported in scaffold envelopes. Closed set: `created`, `skipped`, `overwritten`, `error`, and dry-run equivalents `would_create`, `would_skip`, `would_overwrite`, `would_error`. Existing targets are preserved unless the specific scaffold flag authorizes overwrite, and directory-only scaffold targets never overwrite files. |
| repository registration | The day-zero `striatum repo add <path> --init` flow that registers a target repository into daemon PostgreSQL and creates `.striatum/` scratch for a fresh repo. It is bootstrap, not a live workflow-state bus. Agent assets are installed separately with `striatum skills install` or `striatum plugin install`. |
| cross-round review | A review job whose `reviewer_context_policy` is `cross_round`. The reviewer may retain context across rounds specifically to verify whether previously raised issues were resolved. |
| root review | A review job with no upstream workflow dependency. Root reviews need explicit `needs_revision` policy because there may be no natural author/revision job upstream. |
| job | One executable unit in a workflow, such as draft, review, synthesis, build, test, or human checkpoint. |
| task envelope | A structured instruction packet sent to an agent session for one job or subtask. It includes job id, objective, inputs, allowed write scope, expected artifacts, completion protocol, and stop/block conditions. |
| agent session | A live agent process with conversational or terminal context that may receive one or more task envelopes. |
| native sub-agent | A sub-agent spawned by a supported agent CLI inside an agent session. In v1 it is treated as part of the parent session unless registered as a first-class `striatum` session. |
| first-class session | An agent session registered directly with `striatum`, with its own identity, role, lane, queue claims, artifacts, heartbeats, and audit trail. |
| session slug | The human-readable runtime label stored with an agent session. V1 uses role, lane, and ordinal for uniqueness and scheduling readability; artifact authorship uses the more descriptive role/model/ordinal author line. |
| work packet | The task envelope returned to an identified agent session when it claims or receives work. |
| context doc | A generic workflow- or project-provided document bundle that orients an agent session before or alongside a work packet. Context docs should not be role-specific by default. |
| implementation envelope | The optional `context.implementation_envelope` block in a work packet. It lists reachable downstream jobs' frozen `write_scope` and `expected_artifacts` so design and synthesis lanes can keep implementation recommendations inside the build/review envelope or explicitly flag that the scope must change. |
| shared resource packet block | The optional `context.shared_resources` block in a work packet. It lists the current job's declared shared resources and, when the job is in a parallel group, related parallel jobs with overlapping resource claims so agents can serialize exclusive gates or use declared namespaces. |
| role definition | A reusable artifact that defines an agent's responsibility, stance, allowed behavior, and non-responsibilities. Task prompts may reference role definitions and add job-specific emphasis. |
| run | One execution attempt of a workflow against a repository/workspace. |
| prepared run | A run whose workflow JSON has been validated and snapshotted but whose jobs are not yet claimable because branch confirmation and run start have not both happened. |
| branch confirmation | The explicit operator confirmation that a run should proceed on a named branch. Gates claims before `run start`. Originally framed as a human gate; the actor is the operator role (agent CLI in current practice), not necessarily a person. |
| records-only branch confirmation | V1 branch confirmation behavior: `branch confirm` records the requested branch and reports the detected current git branch, but does not create, switch, commit, push, merge, or rebase. |
| state store | The coordination database for runs, jobs, messages, events, verdicts, process metadata, and artifact references. Per D094 / RFC 0043 it lives in the daemon-owned PostgreSQL instance under a `repository_id` scope. |
| state database | The concrete state store: the daemon-owned PostgreSQL instance (RFC 0033 + RFC 0043). Legacy SQLite databases and their local-state files are completely retired and not supported. |
| event log | The append-only event record (`events`) of facts that happened during a run, such as job started, message sent, verdict recorded, or workflow stopped. Stored in the daemon DB under the run's `repository_id` scope. |
| message bus | The daemon-owned local communication layer used by agents, coordinators, and adapters for live structured messages. It is not the repository artifact layer. |
| message queue | The actionable queue for work delivery and coordination messages, stored in the daemon DB. Queue messages can be pending, claimed, acknowledged, blocked, completed, released, expired, canceled, or dead. |
| work message | A queue message of kind `work` that makes one workflow job claimable by a matching session. |
| claimable work | Pending work messages whose run is started, dependencies are satisfied, and target role/lane match an active session. |
| lease | A time-bounded claim on a queued message or job. Leases prevent two agents from taking the same work and allow recovery if a session dies. |
| acknowledgement | The transition where a session accepts claimed work and moves the job from claimed to running via `ack`. Completion is invalid until work has been acknowledged. |
| heartbeat | A liveness update that refreshes the session timestamp and extends an active lease during long work. |
| lazy lease expiry | The original V1 policy where commands detect and expire stale leases during normal mutations. In the daemon-required runtime, `recovery.sweep` and the Go resident recovery scheduler apply the same lease-expiry behavior against daemon-owned PostgreSQL. |
| stale lease | An expired or abandoned lease whose job cannot safely be requeued automatically, especially when repo-write scope may have been touched. |
| mutation command | A binary command that changes orchestration state, such as `claim-next`, `ack`, `block`, `complete`, or `verdict`. |
| command request | An idempotency record for a CLI mutation attempt, used to return the same result when an agent repeats the same request id and payload. |
| message | A structured communication record in the state store, such as a blocker, review verdict, finding, handoff, or human checkpoint request. |
| event | An append-only state transition record, such as job started, message sent, verdict recorded, or workflow stopped. |
| marker | A durable summary artifact indicating that a job reached a terminal state. Markers are useful provenance, but not the live message bus. |
| blocker | A recorded reason a job or run cannot proceed normally. Blockers can be normal blocked-state reports or human checkpoints. |
| open blocker | A blocker whose state is still `open`; `status --json` and `why <blocker_id> --json` surface these for recovery. |
| review gate | A workflow control point that evaluates review verdicts and decides whether to proceed, revise, re-review, stop, or request human input. |
| verdict | A structured review outcome: `accept`, `accept_with_findings`, `needs_revision`, or `reject`. |
| accepting verdict | `accept` or `accept_with_findings`. Downstream jobs gated on review completion require an accepting verdict. |
| non-accepting verdict | `needs_revision` or `reject`. These verdicts either request a revision route, open a human checkpoint, or fail the review/run. |
| verification | "Did the agent produce what the workflow contract demanded?" — the runner-side, mechanical, judgment-free check that the implementation matches the declared design. Surfaces: `striatum workflow validate` (pre-flight schema + structural checks), RFC 0014 post-exit output validation (`expected_artifacts` + review-verdict gates on `complete`), front-matter schema validation in `publish-artifact`, `doctor` consistency checks. Verification refusals are exit codes 3-9, not verdicts. In DDD terms (`docs/DDD.md`), verification lives in the runner's bounded context. |
| validation | "Is the artifact actually addressing the original problem?" — the reviewer-side, judgment-driven assessment that the design matches the higher-level intent. Surfaces: `submit-review` and the four-verdict vocabulary (`accept` / `accept_with_findings` / `needs_revision` / `reject`); `findings` artifacts; (proposed RFC 0018) `review_posture` and `required_review_postures` for typed validation coverage. Validation outputs are `verdicts` rows; the runner records them but never produces them. |
| acceptance | The owner-side, authority-bearing decision that the run's outcome is acceptable. Distinct from validation (peer review) — acceptance is the human stakeholder saying "ship it" or "stop." Surfaces: `decision record --outcome {accepted, rejected, accepted_with_follow_up}`; `human_checkpoint` blockers + `checkpoint resolve`; the `decision` artifact kind with `striatum.decision.v1` front matter. The runner refuses to advance past a `human_checkpoint` blocker without an explicit resolution. |
| submit-review | A convenience mutation command that validates a review job, publishes the review artifact, records the verdict, and applies review-gate behavior in one operation. |
| revision lane | The configured path that applies accepted review feedback after a `needs_revision` verdict. |
| re-review | A second review pass over a revised artifact. A second reject or unresolved revision request stops the workflow by default. |
| human checkpoint | A workflow stop or pause requiring explicit **operator** judgment before continuing. The "human" in the term is historical — the actor is the operator role (agent CLI in current practice; a person via HOW_TO_HUMAN if one is at the keyboard). The schema field name `human_checkpoint` is retained for compatibility; renaming the field is a deferred cleanup. |
| write scope | The set of files or directories a job is allowed to modify. Used to protect same-branch collaboration and dirty worktrees. |
| review-only artifact scope | A write scope for review jobs that permits publishing unique review artifacts but not modifying the source artifacts under review. |
| parallelism policy | The workflow rule that decides whether multiple jobs, including jobs with the same role, may run at the same time. V1 policy is declared parallelism plus disjoint write scopes or review-only artifacts. |
| worktree-isolated job | A repo-write job whose lane sets `worktree_isolation: "per_job"` and whose work packet therefore advertises `worktree_required: true`. The agent must call `striatum worktree create` before publishing artifacts; `publish-artifact` reads files from the per-job worktree but records the logical repo-relative path so artifacts remain valid main-branch provenance. |
| job worktree | The git worktree allocated for a `worktree-isolated job`, tracked in the `job_worktrees` table of the daemon DB under the run's `repository_id` scope. It lives under `.striatum/worktrees/<worktree_id>` and is created via `git worktree add --detach`. Before a repo-write job completes, its worktree HEAD is anchored by fast-forwarding the run branch or pinning `refs/striatum/<run_id>/<job_id>`; non-`--force` release refuses an unreachable HEAD. Lazy lease expiry marks the row `abandoned` for operator inspection without removing the directory after anchoring first; `striatum doctor` flags orphaned and missing-on-disk worktree rows. |
| PTY adapter | An adapter that runs agents in pseudo-terminal sessions. Tmux is the first expected PTY adapter. |
| process contract | The minimum common integration boundary for agent lanes: command, current working directory, environment, stdin, stdout, stderr, exit code, and optional PTY. |
| adapter constraint | A workflow-declared lane requirement, such as network policy, transcript handling, or repository scope, paired with an adapter enforcement result of `enforced`, `advisory_strict`, `advisory`, or `unsupported`. |
| adapter enforcement | The recorded V1 answer to whether an adapter actually enforces a requested constraint. `enforced` means the adapter prevents the constraint from being violated; `advisory_strict` means the adapter takes best-effort steps the agent cannot easily undo (such as scrubbing proxy env vars or setting `STRIATUM_NETWORK_POLICY` / `STRIATUM_REPO_SCOPE` sentinels); `advisory` means the request is visible but externally enforced if at all; `unsupported` means the adapter cannot represent it. |
| advisory_strict | The fourth adapter enforcement level introduced after V1's first three. It signals that the adapter has taken concrete, non-trivial steps toward the constraint (env scrubbing, sentinel env vars) without claiming full sandbox enforcement. Used by the process adapter for `network=forbidden` and `repo_scope=local_only`. |
| transcript | Broad terminal or model-session output. Transcripts are not captured or published by default; curated artifacts are preferred. |
| bootstrap tmux harness | The temporary Engram-incubation script that starts model panes for early design/build work. It is not the generic product control plane. |
| dashboard | An operator-facing status surface. The first dashboard may be TUI; a web dashboard and chat interface are possible later. |
| run dashboard | The V1 implementation of the dashboard term: `striatum dashboard --run-id <id>`, a compact dependency-free terminal renderer over the same daemon-owned Postgres state as `status` and `why`. Refreshes every 2 seconds by default; `--once` produces a single frame to stdout for scripts and CI. |
| graph panel | The optional layered ASCII view of the workflow's job DAG appended to the dashboard frame on wide TTYs (RFC 0016 V1). State-annotated boxes per job, dashed `~~>` back-edges for `needs_revision` cycles. Toggled with `--graph` / `--no-graph` / `--graph-only` / `--graph-style {auto,layered,list,fancy}` / `--graph-no-cycles`. Reused by `striatum run graph --format ascii` for one-shot snapshots. |
| skill bundle | The set of Markdown files a Striatum-aware agent reads to learn how to drive the runner (RFC 0015 V1). Generated by `striatum skills install`; lives at `.claude/skills/<ns>striatum-*/SKILL.md` (Claude Code profile) or as a single `<ns>STRIATUM_AGENT_GUIDE.md` (generic profile). Self-contained: no external URLs, no source-repo dependency. |
| skills manifest | The `.manifest.json` file at the root of each skill bundle (RFC 0015 V1). Records the runner version that generated each file plus the SHA256 of both the rendered output and the unrendered template. Drives `striatum skills install`'s edit-detection (refuse without `--force`) and `doctor`'s `skills_missing` / `skills_outdated` checks. |
| supervisor | A long-lived agent CLI process held alive across multiple work packets via `striatum supervise start` (RFC 0009). State is tracked in the `process_supervisors` table in the daemon DB under the run's `repository_id` scope; allowed states are `starting`, `attached`, `detached`, `lost`, and `stopped`. A partial unique constraint enforces "at most one active supervisor per session". |
| tmux lane | A tmux-backed supervised lane whose live identity is the tmux pane process (`pane_id`, `pane_pid`, and optional start token), not the `tmux attach-session` client used for operator observation and PTY packet delivery. |
| pane liveness class | The derived RFC 0089 health class for a tmux lane: `tmux_ok`, `tmux_session_missing`, `tmux_pane_missing`, `tmux_pane_dead`, `tmux_pane_pid_mismatch`, or soft `tmux_unavailable`. It is computed from tmux session/pane metadata and never from pane text. The associated liveness state is `healthy`, `degraded`, or `lost`; `tmux_unavailable` is degraded until the persistent-miss threshold is reached. |
| tmux probe failure | A typed failure record captured on a tmux probe miss. It carries `failure_class`, optional `exit_code`, optional `errno`, optional `pane_process_alive`, and optional `observed_pane_pid`; downstream status, doctor, send, and rebridge decisions branch on this structured record rather than terminal output. |
| delivery liveness | The packet-delivery health of the supervisor bridge. It is distinct from pane liveness: a tmux pane can remain live and lane-attested while `delivery_liveness` is degraded because the helper-owned attach bridge exited. Tmux-shaped metadata stores this under `tmux.delivery_liveness`; no-tmux/plain metadata may store the same value at top-level `delivery_liveness`. |
| start-token-unverified | A tmux liveness detail meaning the pane is operationally live but Striatum could not verify the pane pid start token. Read surfaces must downgrade lane attestation to `unattested` with reason `start_token_unverified` instead of treating the lane as provenance-attested. |
| attach client | The transient `tmux attach-session` process connected to a tmux lane. It is an observer and byte-delivery handle; it may exit while the lane keeps running, and its output is never workflow state or durable provenance. |
| rebridge | The in-place `supervise.rebridge` repair action for a tmux-backed supervisor whose delivery bridge is degraded while the pane is still live. Rebridge recreates the delivery FIFO if needed and starts a fresh helper attach path without killing, resetting, or respawning the tmux pane. |
| supervised session | An agent session whose lane uses the `process` adapter and whose process is held by a supervisor. Raw provider output is never workflow authority or durable provenance; agent-loop PTY lanes may tee terminal output to private `.striatum/scratch/<supervisor_id>/pty.log` diagnostics. Lease expiry transitions the supervisor row to `lost` without auto-killing the OS process; operator inspection is required. |
| supervisor pipe | Historical named FIFO used for one-shot wrappers. Completely retired under RFC 0088 in favor of native interactive PTY master stdin-submit turn delivery. |
| supervised lane wrapper | A per-tool script that assists the supervisor in maintaining the long-lived process loop. Shipped wrappers live at `.striatum/bin/{claude,codex,agy}-supervised-wrapper.sh` (where `agy` profile reuses the `claude` template structures under `.agy/`). |
| diagnostic envelope | Privacy-safe metadata block recorded as `blockers.payload_json` for every process-adapter blocker (RFC 0014 V1). Carries `process_id`, `command`, `exit_code`, `duration_seconds`, `timeout_seconds`, `missing_artifact_paths`, `review_verdict_missing`, and operator-copyable `recovery_commands`. Never contains child stdout/stderr or model output (D028 preserved by construction). |
| process completion validation | The post-exit check `striatum adapter run` performs after the lane process exits or is SIGTERM'd by timeout (RFC 0014 V1). Compares published artifacts against the job's required `expected_artifacts`, checks for a recorded verdict on review jobs, and inserts a blocker with a structured reason (`process_outputs_missing`, `process_review_verdict_missing`, `process_exit_nonzero`, `process_timeout_exceeded`) plus the diagnostic envelope when any failure condition holds. |
| push auto-dispatch | The supervised-session behavior where `supervise start` for a non-agent-loop `supervised_push` lane atomically claims the next eligible packet, writes it to the supervisor FIFO, records `queue.claimed` plus `supervisor.packet_delivered`, and returns an `auto_dispatch` summary without requiring a manual `claim-next` + `supervise send`. |
| publish-on-behalf | Historical RFC 0040 operator-side composite action: compose `ack` + `publish-artifact` + (for review jobs) `verdict` or (for non-review jobs) `complete` using the same lease/message ids the agent received. The SQLite-bound `dogfood.publish_on_behalf` RPC is removed from the production daemon contract; operators use primitive daemon methods until a PostgreSQL-native composite is accepted. |
| surgical recovery | Historical RFC 0040 operator-side composite action for the lease-expired-under-active-load case (dogfood-038 intervention #5): atomically reactivate an expired lease, transition the supervisor row from `lost` back to `attached`, and restore queue message + job state to post-ack-pre-complete. The SQLite-bound `dogfood.surgical_recovery` RPC is removed from the production daemon contract; ordinary daemon recovery tools are the supported path until a PostgreSQL-native replacement is accepted. |
| supervised-progress heartbeat | Daemon-side mechanism introduced by RFC 0040 V1 that watches the supervised wrapper's stdout log file mtime and refreshes the active lease automatically when growth is observed within `idle_threshold_seconds`. Lets long-running supervised work (e.g., `make test`) avoid lazy-lease expiry while the wrapper's own heartbeat thread is blocked. File-mtime polling in V1; sidecar-signal an option for V1.5. |
| dogfood-lifecycle chat tools | Historical RFC 0040 composite web-chat tool names (`run_prepare`, `run_start`, `register_session`, `supervise_start`, `claim_next`, `ack`, `publish_artifact`, `verdict`, `complete`, `supervise_stop`, `run_summary`, `evidence_export`) from the retired Python local service. Current production agents use daemon MCP/RPC primitive methods or daemon-backed CLI fallbacks; the composite dogfood helper names are absent from the production daemon contract until a PostgreSQL-native replacement is accepted. |
| harness profile fragment | A per-tool-family entry in the bundled workflow-template catalog (RFC 0040 V1) carrying the recommended `native_delegation.mode` and `native_delegation.instruction` for that tool family. The fragments encode the "no-questions" instruction for codex / claude_code / agy and add the front-matter completeness callout. `workflow generate` consumes them by default; the Python-era `workflow upgrade` CLI that backported them into existing workflow files is retired. |
| model portability | The design goal that workflows, state, and coordination semantics survive swapping model providers, model versions, and model CLIs. |
| harness profile | An optional, advisory map of native-tool capabilities and constraints surfaced to a lane via `harness_profile_id` (RFC 0010 V1). The runner exposes the profile body as a `harness_profile` block in work packets but does not branch on it; profiles are configuration, not execution authority. |
| tool family | The closed RFC 0010 V1 set `{generic, codex, claude_code, agy}` that names a profile's intended terminal-agent CLI. Validation rejects other values; future families require a separate decision. |
| native delegation | A tool-internal mechanism (Claude Code sub-agents, Codex custom agents, agy custom instructions) by which a parent session decomposes a task. Native delegation stays internal to the parent Striatum session in V1; it does not register as new Striatum sessions, leases, or artifacts. |
| harness improvement proposal | A `harness_improvement_proposal` artifact (RFC 0005 / 0010) that records friction in prompts, workflows, defaults, or documentation observed during a dogfood run. Proposals are advisory until reviewed and accepted. |
| local service | The Go HTTP service mounted by `striatumd` on the daemon's loopback MCP listener. It shares the daemon bearer token, rejects non-loopback hosts, routes reads and allowed mutations through daemon RPC, and streams events from daemon `run.events`. The standalone `striatum serve` process is retired. |
| service mutation gate | The `STRIATUM_DAEMON_WEB_ALLOW_MUTATIONS=1` daemon-startup setting for the loopback web service. Without it, mutating HTTP routes such as `POST /v1/invoke` and `POST /workflows/generate` fail closed. New mutating daemon methods default to blocked from web mutation unless intentionally exposed. |
| local web UI | The bundled Go-served local web surface mounted by `striatumd` on the loopback HTTP listener, plus an optional read-only RFC 0085 tailnet identity listener on `web-ui.sock`. Current Go routes cover status/run pages, daemon-backed run JSON/SSE reads, raw artifacts, and workflow-template/generator endpoints; richer Python-era pages remain retired until reintroduced by a Go route. |
| frontend island | Historical RFC 0038 V1 term for the retired React/Vite island architecture. The current Go web service does not ship the removed `src/striatum/web/frontend` tree or a Node build loop; current templates and static assets live under `go/pkg/webassets/`. |
| tree browser | Historical RFC 0038 V1 island for `/view/`. The current Go web service does not ship the retired `/view/` page unless a future Go route reintroduces and documents it. |
| workflow chooser | Historical RFC 0038 V1 React island for `/workflows/new`. The current Go service keeps the generator endpoints (`GET /workflow-templates`, `POST /workflows/generate/preview`, `POST /workflows/generate`) but does not currently ship the retired wizard page. Generator writes require the daemon web mutation gate. |
| graph editor | Historical RFC 0038 V1 React Flow island for `/workflows/edit/<path>`. The current Go service keeps workflow-template and generator endpoints, but does not ship the retired graph-editor page. |
| code viewer | Historical RFC 0038 V1 Shiki-based island for `/view/<path>`. The current Go service does not ship the retired code-viewer page. |
| frontend toolchain | Historical RFC 0038 V1 / D092 Vite + React + TypeScript toolchain. It is not present in the current Go-only tree; current web changes use Go templates/static assets and Go tests. |
| bundle hash manifest | Historical RFC 0038 V1 Vite bundle drift detector. The current Go-only web assets are embedded from `go/pkg/webassets/`; there is no current `manifest.sha256` bundle gate. |
| Striatum daemon | The local foreground daemon process (`striatumd`), normally installed as a systemd user service by `striatum daemon install`. Per D094 / RFC 0043 it is a hard prerequisite for every Striatum verb; CLI, MCP, and local web surfaces are clients, the daemon is the single writer for all live workflow state, and the V1 `--no-daemon` direct path is retired. The daemon owns the per-machine PostgreSQL substrate (RFC 0033) plus per-repo workflow tables under a `repository_id` scope, provides multi-repository read visibility, recovery sweeping, capability-gated MCP mutation tools, and apply receipts. Bundled / Dockerized distributions and hosted (network-accessible) semantics remain out of scope. RFC 0048 completed the production handler port in v1.55.0; legacy SQLite handling is completely retired, and registrations reject any old SQLite files. |
| daemon core | The implementation of the daemon process. The production daemon is Go-only (striatumd); all legacy Python core and client modules have been completely retired and deleted. |
| daemon registry | Central per-machine daemon state for registered repositories, client tokens, capabilities, metadata-only audit rows, audit segment manifests, scheduler cursors, and daemon metadata. Hosted in the daemon DB (RFC 0033). |
| daemon DB | The daemon-owned PostgreSQL database. Per D094 / RFC 0043 it holds both daemon-global state (registry, audit, capability, scheduler, RPC-session) and per-repository workflow tables under a `repository_id` scope; it is the single source of authoritative live state. Configure with `STRIATUM_DAEMON_DB_URL`, daemon config, or `--postgres-url`. |
| daemon RPC envelope | The RFC 0030 JSON request/response shape shared by daemon transports. Requests carry `schema_version`, `request_id`, dotted `method`, object `params`, optional `capability_token`, and `deadline_ms`; responses echo version/request id and carry either data or a stable error object. |
| method registry | The code-owned table of daemon RPC methods, required capability, repository-scope behavior, params schema version, audit class, minimum envelope, and deprecation state. `daemon.describe` publishes it with a stable `methods_etag`. |
| capability scope | The daemon authorization boundary attached to a token and a method. Current capabilities are `read`, `write`, `review`, `claim`, `apply`, `admin`, `recovery`, and `surgical_recovery`; tokens may be daemon-global or scoped to one registered repository. |
| request log | The PostgreSQL daemon table that records one row per RPC request id, including method, client, repository, params hash, response hash, decision, envelope version, daemon version, schema version, and retention deadline. It is metadata-only, not transcript storage. |
| daemon-owned supervisor | A supervised agent process whose ownership metadata lives in the daemon DB. Lane-attestation and packet-delivery paths read the same daemon-DB state under the run's `repository_id` scope. |
| supervisor pointer | The `process_supervisor_pointers` row in the daemon DB that links a daemon-owned supervisor id to a run/session, pid identity, and current supervisor state under the run's `repository_id` scope. |
| sealed-apply authority | The daemon capability and signing-key boundary that may apply a reviewed patch only after digest, verdict, base-tree, write-scope, and apply-gate checks pass. It is an AI guardrail, not proof against a malicious local operator. |
| apply receipt | A daemon-owned record and evidence artifact describing an accepted sealed apply: repository, run/job, patch artifact, patch digest, base tree, resulting tree when known, signing key id, signature, state, and denial reason when refused. |
| daemon signing key | The local Ed25519 key the daemon uses for sealed apply receipts. | daemon DB migration | The daemon-owned, forward-only migration set for the RFC 0033 daemon DB. Startup applies pending migrations and refuses to run when the on-disk daemon schema is newer than the daemon binary. The old SQLite cutover spellings are fully removed. |
| substrate version | The daemon DB schema-version integer recorded in each daemon audit row and surfaced by `striatum doctor`. Distinct from the daemon binary version. |
| first-run smoke | Retired Python-era name for the bootstrap check once exposed as `striatum doctor --first-run`. Current Go diagnostics use `striatum daemon status`, `striatum doctor --verbose --json`, and an explicit `striatum repo add <path> --init` registration check. |
| operational scratch | The post-D094 role of `.striatum/` next to a target repository: PTY FIFOs (`scratch/`), pidfiles, transient supervisor stdout, optional lane wrappers (`bin/`), and plugin scratch. The daemon runtime token lives under the daemon runtime directory as `client-token`. Nothing here is durable workflow truth. |
| daemon-required CLI | The post-D094 default and only CLI behavior. Every verb routes through the daemon RPC envelope under token authorization; the daemon is the single writer. | system Postgres | The operator-installed PostgreSQL service the RFC 0033 V2 daemon connects to through `STRIATUM_DAEMON_DB_URL`, daemon config, or an explicit `--postgres-url` client surface. The daemon owns schema and roles, but it does not manage the Postgres lifecycle. |
| bundled distribution | A deferred packaging shape that would ship Striatum's daemon together with PostgreSQL, either through Dockerized composition or an embedded Postgres binary. Out of scope for RFC 0033 V2. |
| repository tenant | A registered target repository in the daemon registry. | client capability | A daemon authorization grant for a client token. Current capability vocabulary is `read`, `write`, `review`, `claim`, `apply`, `admin`, `recovery`, and `surgical_recovery`; method registry entries declare which one they require. |
| daemon audit | Metadata-only per-machine evidence of daemon requests. | global dashboard | The daemon-backed `striatum dashboard --all` read view that groups registered repositories and reports daemon/Postgres runs, blockers, claimable jobs, stale leases, and degraded repositories. It requires daemon read authorization. |
| cross-repo run | A daemon-mediated run spanning two or more registered local repositories. | cross-repo coordinator | A coordinator session for a cross-repo run whose read scope spans all participating repositories. It routes work and escalation across participants; it does not perform role work or create cross-repo provenance claims. |
| MCP mutation capability | A daemon capability that permits MCP `tools/call` to mutate state, such as `write`, `review`, `claim`, `apply`, `admin`, `recovery`, or `surgical_recovery`. `read` remains introspection-only. |
| effective tool set | The daemon MCP tool list visible to a token after intersecting the method registry with the token's capability grants, repository scope, and production-support visibility filter. | MCP mutation surface | The agent-facing daemon/chat tool surface that exposes capability-gated methods through `tools/list` and `tools/call`. RFC 0036 teaches it through the `striatum-mcp` skill and preserves the rule that direct database writes are never allowed. |
| operator-confirmed chat mutation | A web mutation that requires the daemon web mutation gate, a model-supplied `confirm_write: true` where applicable, and a separate browser-side operator gesture before the server executes the write. |
| mutation-not-allowed path | The fail-closed behavior when the service lacks mutation authority: mutating chat tools are hidden from the tool list, and stale or crafted write calls return `mutations_disabled` without writing files. |
| Striatum corpus | The closed set of Striatum software-building artifacts exported for optional external retrieval consumers: RFCs, decision-log rows, operator reports, run summaries, audit-chain entries, changelog entries, ubiquitous-language terms, harness-friction patterns, and recent commits (RFC 0044 V1 nine-kind set). |
| Striatum corpus export | The redacted JSONL bundle plus verifying `manifest.json` produced by `striatum corpus export --since <ref> --out <dir>` (RFC 0044 V1). Operator-triggered, replay-stable, never streamed to an external service. |
| memory augmentation | An optional retrieval surface an operator or workflow may consult for repository-grounded context. It never owns workflow state, never gates a state transition, and never appears in Striatum source. Engram is the first reference consumer under RFC 0041 / 0044. |
| augmentation-not-dependency | The non-negotiable invariant that Striatum runs unchanged when any external memory or retrieval consumer is missing, slow, or unreachable. Pinned by `tests/test_cli_corpus_export.py::test_no_engram_imports_or_memory_capabilities_in_striatum`. |
| private project memory | Context available to one operator or environment but not shared through repository docs, daemon state, durable artifacts, or explicit corpus exports. It can make a local session more informed, but it is not provenance, not live workflow state, and not a dependency Striatum may require. If a claim matters to future operators, crystallize it into a repo-shared artifact or decision instead of leaving it in private memory. |
| corpus contract version | The bundle-level integer that names which Corpus Contract a manifest declares. V1 is implied (RFC 0044). V2 is named in [RFC 0057](../rfcs/0057-corpus-contract-v2.md) as a scaffold of open decisions. |
| panel_role | A review job's seat role within a quorum panel: `gating` (counts toward the quorum and can block finalize) or `advisory` (informs but cannot block). It defaults to `gating`, so existing panels are unchanged; see [RFC 0132](../rfcs/0132-gating-advisory-reviews-quorum-dissent-protection.md) and D214. |
| gating seat / gating review | A review seat whose verdict counts toward the panel quorum and can block the downstream gate job from finalizing. A live gating seat blocks the barrier; quorum may skip a structurally-dead gating seat against the abstention budget, never a merely slow one. |
| advisory seat / advisory review | A review seat declared `panel_role: advisory` that is excluded from the quorum denominator: it informs the panel but cannot block finalize. |
| quorum | The frozen declared-seat denominator a panel must satisfy to finalize, read from the workflow snapshot's job dependencies and fixed at run prepare so a seat cannot be added or dropped after fan-out. See [RFC 0132](../rfcs/0132-gating-advisory-reviews-quorum-dissent-protection.md) and D214. |
| max_gating_abstentions | A per-gate-job budget (default 0) for how many gating seats quorum may finalize past when they are structurally unrecoverable. Because a non-zero budget lets finalize proceed past unfilled gating seats, a value > 0 must be a fixture-diff-visible explicit author choice and is rejected at lint time unless the job also sets `allow_gating_abstentions: true` (D214). |
| dissent ledger | An append-only, forward-written record of blocking verdicts (`needs_revision` / `reject`) keyed on the stable `workflow_job_id`, written co-transactionally with the verdict. A live dissent keeps a panel blocked wherever recovery later moves the seat's lineage; it can only be cleared by a new current-seal accepting verdict. Created by migration 0032 (RFC 0132 / D214/D215). |
| advisory minority report | The `advisory_minority_report.v1` front-matter artifact a panel finalize authors to record the advisory tally that does not count toward the gating quorum but is never silent: each advisory seat's verdict and rationale excerpt, which Layer C guard fired (or `none`), and the resolved `advisory_outcome` (`must_escalate` when a guard fired, `advisory_noted` otherwise). It is pinned as a required `expected_artifact` on the synthesis/gate packet, so the publisher refuses with exit code 6 if it is omitted. See [RFC 0132](../rfcs/0132-gating-advisory-reviews-quorum-dissent-protection.md) Layer C and D214. |
| advisory guard | One of three Layer C checks evaluated co-transactionally with each panel verdict that lets an advisory reviewer stop the line without ever auto-flipping a verdict: `advisory_corroborated_abstention` (a gating abstention co-occurring with a live advisory `needs_revision`/`reject`, reclassified to `must_escalate`), `unanimous_advisory_reject` (every submitted advisory seat rejecting, blocking finalize even under full gating accept), and `advisory_only_panel_ungrounded` (a gate whose panel has no gating seats). A fired guard opens an operator-resolvable `blocked`-severity blocker on the downstream gate (the `checkpoint resolve` shape) plus an `escalation_inbox` row; it never silently wedges and never auto-`needs_revision`s the implementer (RFC 0132 Layer C / D214). |
| must_escalate | The advisory outcome a fired advisory guard resolves into: a gating abstention or panel state that must reach an operator (an escalation), never silently folded into the abstention budget or auto-finalized (RFC 0132 Layer C). |
| join manifest | The `join_manifest.v1` provenance artifact emitted as the sole output of a sealed fan-in barrier fire, recording the barrier's in-edges with each sibling's frozen seal/attempt, staging ref, and the frozen base/tree/commit the assembly folded onto. It is provenance only (no semantic netting); see [RFC 0133](../rfcs/0133-fan-in-deferred-join-barrier-and-manifest.md) and D213/D215. |
| staging ref | A sibling's staged contribution ref (under `refs/striatum/staged/<run>/<workflow_job_id>/<attempt>`) pending fan-in barrier assembly. A superseded attempt is renamed into a voided namespace so recovery can explain why it no longer contributes (RFC 0133). |
| frozen tip | The frozen run-branch base/tip commit a fan-in barrier in-edge is sealed against, recorded once at fan-out in an immutable freeze record. A staged contribution must descend from it; one that does not is refused as base drift (RFC 0133). |
| claim lattice | The `VERIFIED > ASSERTED > DESIGNED` ordering over a claim's status (RFC 0134 / D227). It separates *whether a thing is built* from *whether someone decided to build it*: the decision-log "accepted" rung is `DESIGNED`, a structured-read producer assertion is `ASSERTED`, and only sealed mechanical evidence earns `VERIFIED`. The point of the ordering is that a stage may only ever *lower* a claim's effective status, never raise it — promotion is the "sealed mint", refused without bound evidence. Carried by a `claim_ledger` artifact and enforced by a pure validation surface (provenance lint + daemon-writer rules); no command execution is on the gate path. |
| VERIFIED | The top claim-lattice rung (RFC 0134). A claim is VERIFIED only with a bound receipt (`receipt_ref`) and an `evidence_digest` that matches the claim's `bound_input_digest` — the receipt is bound to *these* inputs. VERIFIED auto-decays to ASSERTED when the bound input hashes change. At the run-completion gate READ, VERIFIED additionally requires **two signals**: the sealed receipt records exit-0 AND an independent re-execution agreement under a *strict* verifier sandbox; a lone exit-0, a non-strict posture, or a missing/wedged receipt degrades to ASSERTED, and a timeout / envelope-violation is INDETERMINATE → ASSERTED, never VERIFIED. The receipts are minted off the gate path by the disposable sandboxed verifier lane; the daemon only reads them. |
| ASSERTED | The middle claim-lattice rung (RFC 0134): a producer states the claim from a structured read of source, with no sealed mechanical evidence. It is the default ceiling for an unwitnessed claim — authoring a claim VERIFIED without bound evidence is refused (the provenance lint), so an honest unwitnessed claim asserts at most ASSERTED. |
| DESIGNED | The lowest claim-lattice rung (RFC 0134): a planned or decided intention with nothing built or measured behind it — the decision-log "we decided to" status. It carries no evidence requirement; the lattice exists to stop DESIGNED silently reading as done. |
| claim ledger | A durable, append-only artifact (kind `claim_ledger`, RFC 0134 / D227) carrying a run's claims with a status on the claim lattice plus each claim's bound evidence (`bound_input_digest`, optional `receipt_ref` / `evidence_digest`). The daemon validates it (per-row shape + provenance lint at the publisher, exit code 6) and enforces the cross-seal lattice rules at the writer: the `ledger_seal` is monotonic (append-only), and a claim is demotable but never self-promotable across seals. It validates, it never executes. |
| receipt | The sealed evidence artifact (kind `receipt`, RFC 0134) a VERIFIED claim binds to. It records a tamper-evident transcript — argv, resolved binary hash, exit code, stdout digest, and cwd tree-sha — plus a `seal_digest` the claim's `evidence_digest` must equal. The daemon never executes a check to produce a receipt; receipts are minted off the gate path by the disposable sandboxed verifier lane, and the claim ledger merely names one. |
| verifier lane | The disposable, sandboxed lane (RFC 0134 / D227) that runs an operator-allowlisted check OFF the daemon's gate path and mints a `receipt`. It is the only place command execution happens in the verification feature; the daemon validates the sealed receipt, it never runs the check. Built as `go/pkg/verifier` + the lane-side `striatum verifier run` command and persisted as a `verify` job type (owner bundle 0016). |
| check allowlist | The operator-curated, git-tracked, content-addressed set (kind `striatum.verifier_allowlist.v1`) of checks a verifier lane may run (RFC 0134 / D227). Each entry pins an exact argv and the sha256 of the resolved binary, so a workflow NAMES a check by id but never AUTHORS the executed bytes — an unknown id or a binary whose hash drifted from the pinned value is refused before anything runs. |
| verifier sandbox posture | The RESOLVED, attested security envelope a verifier lane ran a check under (RFC 0134 / D227): which mechanism applied (bubblewrap / systemd-run / unshare+ulimit / none) and which guarantees actually held — no-network, no-new-privileges, read-only-except-scratch, and cgroup/cpu/mem/wall-clock caps so a runaway check kills its own scope, not the daemon. Recorded in the receipt and read by the gate; a non-*strict* posture caps the receipt at ASSERTED — it can never earn VERIFIED. |
| two-signal verification | The RFC 0134 / D227 rule that the top claim rung VERIFIED requires TWO independent signals — a sealed exit-0 receipt PLUS an independent re-execution agreement under a strict verifier sandbox — so a lone exit-0 earns only ASSERTED. The verifier lane runs each check twice and records the agreement; the gate reads it. |

## Distinctions

- **Engram** is the incubation history and an optional augmentation consumer
  of corpus exports; **striatum** is a generic local runner with no runtime
  dependency on Engram. Engram's plan to become Striatum's local memory
  layer lives in `~/git/engram/STRIATUM_MEMORY_ROADMAP.md`; that roadmap
  cannot break the augmentation-not-dependency invariant — Striatum must
  still run unchanged when Engram is missing, slow, or unreachable.
- **Live state** is the daemon-owned PostgreSQL instance under a
  `repository_id` scope (D094 / RFC 0043); `.striatum/` next to a target
  repo is operational scratch only. **Durable provenance** is committed
  or commit-ready repository artifacts.
- A **message** is live coordination state; an **artifact** is durable project
  provenance.
- A **session slug** identifies a runtime session; an **artifact author** is a
  byline for humans reading committed artifacts.
- A **marker** is an artifact summarizing completion; it is not sufficient as a
  message bus.
- An **agent lane** is portable configuration; it should not be treated as a
  hardcoded provider identity.
- **Branch confirmation** in V1 is records-only; git branch creation and
  switching remain external human/operator actions.
- **Adapter constraints** are not automatic sandboxes. Treat `advisory` as a
  visible request that still needs external enforcement.
- The **deterministic coordinator** enforces gates; the **AI coordinator**
  helps the human move the workflow through those gates.
- **agy** (Antigravity) is the canonical claude-shaped tool family that replaced
  the retired `gemini_cli` family (RFC 0088 / D150). Its agent-loop bootstrap is
  delivered as `--prompt-interactive` argv (not PTY stdin-submit), and its MCP
  server is configured through a fresh project-level `.gemini/settings.json`
  (gemini `httpUrl` schema), not a `--mcp-config` flag.
- The **`single_shot` capability**, the agent-loop **turn-driver** (F42-F45),
  and the **`--print`/`exec` supervised wrapper** are **retired** (RFC 0088 /
  D148, D150): agent lanes are daemon-owned long-lived interactive PTY/agent-loop
  sessions, not per-packet fresh processes. (The RFC 0086 *conversation*
  turn-driver for multi-party floor management is a separate, live mechanism.)
