# FALSIFIER - multi-campaign supervision authority boundary

author: falsifier-reviewer-001

## Claim Challenged

The holder's Claim 1 and combined gate claim say the Level-1 shortlist is ready for product-decision/RFC drafting around stage-scoped authority receipts, fresh replay, quarantine, and cross-surface contradiction proof. The authority-boundary claim is only sound if the next gate cannot turn an `AuthorityReceiptV1` artifact, ticket body, dashboard row, or replay summary into current permission to launch or advance Striatum workflows.

## Concrete Evidence

The current runner boundary is daemon-first: `docs/how-to/how-to-agent.md:52-60` says authoritative live state lives in daemon-owned PostgreSQL and the runner, not prose or terminal output, advances state; `docs/how-to/how-to-agent.md:64-73` says the daemon is the single writer and `work.complete` is the state transition. Artifact paths and bylines are required outputs (`docs/how-to/how-to-agent.md:228-235`), not authority-bearing workflow state.

The Level-1 authority deepening acknowledges exactly the dangerous split. It says the first concrete step is to draft an `AuthorityReceiptV1` artifact contract and worked transition example, while a later product build would make receipts daemon-enforced instead of design provenance (`deepened/deepen_1/DEEPENED.md:24-26`). It also names evidence laundering as the hard risk when receipts renew from stale, partial, or prose-only claims (`deepened/deepen_1/DEEPENED.md:20-22`).

The proposed feature is not merely advisory in the motivating scope: the human asks for a meta-agent that, after a human accepts an arc, can run design, build, verifier, and slice workflows until stop conditions (`MULTI_CAMPAIGN_SUPERVISION_DESIGN_SCOPE_PRD.md:36-44`; `PROBLEM_BRIEF.md:15-18`). The same source asks Level 1 to define what the meta-agent may start, sequence, scaffold, pause, quarantine, update, or escalate (`MULTI_CAMPAIGN_SUPERVISION_IDEATION_BRIEF.md:64-68`; `PROBLEM_BRIEF.md:42-43`).

The holder tries to narrow the immediate gate, but it does not make the proof-only supervisor the required next-stage floor. The synthesis's own wildcard says v1 could have no workflow-launch authority and emit only receipts, replay failures, quarantine rows, and contradiction reports while humans still launch ordinary workflows; only after that proof-only version keeps arcs legible should launch authority be considered (`IDEATION_SYNTHESIS.md:95-102`). The holder mentions this only as a non-claim that there is no approval to run outside ordinary daemon authority (`HOLDER.md:150-160`), not as a mandatory stop condition on the next RFC.

## Counterexample

A next RFC can stay inside the holder's literal non-claims and still cross the boundary:

1. Define `AuthorityReceiptV1` as a durable artifact/ticket section with allowed actions, expiry, evidence handles, and stop triggers, as suggested by the deepening artifact.
2. Let a fresh replay lane validate that artifact against selected daemon/artifact/Git/ticket handles and write a replay pass result.
3. Treat the pass result as renewal authority for a coordinating agent to call existing daemon workflow-launch or ticket/scaffold/update routes under the already human-accepted arc.

No new daemon schema or route map is required for that RFC draft to be internally coherent, and no dashboard or ticket row is called live state. But the receipt has become ambient permission anyway: the authority source is a provenance artifact plus replay prose, not a current daemon-scoped receipt row or capability checked at the moment of each launch/advance. If the receipt is stale, copied into a ticket, or contradicted by later daemon state, the only proposed protection is another artifact-level contradiction check. That is precisely a shadow workflow state machine beside the daemon.

## Strongest Rebuttal

The holder has a serious rebuttal. It explicitly says the current clearing result is only permission to draft a product decision or RFC, not architecture, build readiness, source changes, daemon schema, UI, ticket backend, implementation tickets, or approval to run multi-campaign supervision outside ordinary Striatum daemon authority (`HOLDER.md:5-15`, `HOLDER.md:150-164`). The seed also says this falsification gate does not authorize implementation and must stop before design-to-build readiness (`SEED.md:36-41`). The workflow-selection artifact adds a product-decision checkpoint and a design-to-build readiness checklist before implementation tickets (`MULTI_CAMPAIGN_SUPERVISION_WORKFLOW_SELECTION.md:104-115`).

That rebuttal prevents immediate build authorization, but it does not close the authority boundary. The next RFC/product-decision gate is exactly where the permission model will be defined, and the holder's current four-item shortlist still permits the first design object to be an artifact contract whose daemon-enforced status is deferred.

## Unanswered Gap

The holder should not clear on the authority/daemon-boundary lens unless it adds this stop condition for the next gate:

A receipt, replay pass, quarantine row, ticket, dashboard row, or contradiction report is provenance only until a current daemon-scoped authority object or explicit human/product decision authorizes the exact stage action. The first acceptable RFC must either be proof-only with no workflow-launch authority, or specify daemon-state enforcement, current receipt reconciliation, expiry refusal, and human-confirmed authority expansion before any coordinating agent may start, sequence, scaffold, promote, or mark work done.

Without that floor, the proposal can advance to an RFC that calls itself local-first and daemon-respecting while letting artifact receipts and replay summaries become the real permission source.
