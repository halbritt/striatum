# FALSIFIER - RFC 0136 narrowed-uniqueness and chain-head RI gap

author: falsifier-reviewer-001

## Gate result

Material challenge: the holder SPEC does not yet preserve every existing
integrity guarantee through the partition-key reshape. It proves that PostgreSQL
forces the reshaped keys, but then treats the lost narrow database constraints as
acceptable application invariants. That is not the same guarantee. The current
schema database-enforces `(repository_id, event_id)` identity on `events`,
database-enforces globally unique `audit_log.row_hash`, and database-enforces
`repo_event_chain_heads.last_event_id -> events(repository_id, event_id)`. The
holder's replacement shape allows each of those guarantees to fail unless the
build adds an equivalent in-DB guard.

This should stop the gate from clearing.

## Claim attacked

The holder's core claim is that the forced PK/UNIQUE reshape "preserves every
existing integrity guarantee" while moving the invalidated chain-head FK into
the Go/SD write path (`HOLDER.md:29-39`). H1 names the forced reshape:

- `events`: `PRIMARY KEY (repository_id, event_id, created_at)`
- `audit_log`: `PRIMARY KEY (audit_id, ts)` and `UNIQUE (row_hash, ts)`

(`HOLDER.md:52-62`).

H3 then says dropping the SQL FK from `repo_event_chain_heads` loses "no real
guarantee" because every known writer inserts the event and advances the head in
one transaction (`HOLDER.md:113-147`).

Those statements skip the exact hazard the RFC itself calls load-bearing:
after the reshape, the database no longer enforces event-id uniqueness per repo
or global `row_hash` uniqueness, and the RFC leaves open whether to re-assert
that guard or rely on the sole-writer invariant
(`docs/rfcs/0136-range-partition-events-audit-log-by-time.md:146-155,
423-428`). The holder does not close that open question with an equivalent
database constraint.

## Concrete refutation

### 1. `audit_log.row_hash` duplicates can slip across partitions

Current source has a true global uniqueness constraint:

```sql
CREATE TABLE IF NOT EXISTS striatumd.audit_log (
  audit_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  ts timestamptz NOT NULL,
  ...
  row_hash text NOT NULL UNIQUE,
  segment_id bigint NOT NULL REFERENCES striatumd.audit_segments(segment_id)
);
```

(`go/pkg/db/sql/0001_baseline.sql:83-100`).

The holder's reshaped constraint is only `UNIQUE (row_hash, ts)`. A minimal
partitioned-table reproducer accepts the duplicate that today's table rejects:

```sql
CREATE TABLE audit_log_p (
  audit_id bigint NOT NULL,
  ts timestamptz NOT NULL,
  row_hash text NOT NULL,
  PRIMARY KEY (audit_id, ts),
  UNIQUE (row_hash, ts)
) PARTITION BY RANGE (ts);

CREATE TABLE audit_log_p_2026w01 PARTITION OF audit_log_p
  FOR VALUES FROM ('2026-01-01') TO ('2026-01-08');
CREATE TABLE audit_log_p_2026w02 PARTITION OF audit_log_p
  FOR VALUES FROM ('2026-01-08') TO ('2026-01-15');

INSERT INTO audit_log_p(audit_id, ts, row_hash)
VALUES
  (1, '2026-01-02 00:00:00+00', 'same-hash'),
  (2, '2026-01-09 00:00:00+00', 'same-hash');
```

That is not a hypothetical PostgreSQL edge; it is the direct consequence of the
holder's own H1 rule. The strongest holder rebuttal is that `append_audit_row`
computes SHA-256 over the prior hash and timestamp, so a duplicate row hash is a
hash break and operationally infeasible. That explains why the application may
never produce the duplicate on the happy path. It does not preserve the existing
database guarantee. Today's DB catches a collision or bad owner/backfill insert
globally; the proposed DB shape catches it only when the duplicate has the same
`ts`.

### 2. `events(repository_id, event_id)` stops being row identity

Current source makes `(repository_id, event_id)` the primary key
(`go/pkg/db/sql/0005_repo_local_workflow_state.sql:324-342`). The holder changes
the key to `(repository_id, event_id, created_at)`. A partitioned table with that
key accepts two rows with the same logical event id in different time buckets:

```sql
CREATE TABLE events_p (
  repository_id text NOT NULL,
  event_id bigint NOT NULL,
  created_at timestamptz NOT NULL,
  payload_json jsonb NOT NULL DEFAULT '{}'::jsonb,
  previous_hash text,
  row_hash text,
  PRIMARY KEY (repository_id, event_id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE events_p_2026w01 PARTITION OF events_p
  FOR VALUES FROM ('2026-01-01') TO ('2026-01-08');
CREATE TABLE events_p_2026w02 PARTITION OF events_p
  FOR VALUES FROM ('2026-01-08') TO ('2026-01-15');

INSERT INTO events_p(repository_id, event_id, created_at, row_hash)
VALUES
  ('repo_1', 42, '2026-01-02 00:00:00+00', 'h1'),
  ('repo_1', 42, '2026-01-09 00:00:00+00', 'h2');
```

The normal sequence path should not emit that pair, but again the existing DB
constraint is what makes the pair impossible. After the reshape, a sequence
reset, owner-bundle copy mistake, fixture insert, or any non-append writer can
create duplicate logical event ids. That breaks row identity for existing code
and schema facts that still carry only `repository_id,event_id`. The sharpest
example is the chain head itself: `repo_event_chain_heads` currently stores only
`repository_id` and `last_event_id`, and its SQL FK references exactly
`events(repository_id,event_id)` (`go/pkg/db/sql/0006_events_chain_anchors.sql:
72-81`). If the parent can contain two `(repository_id,last_event_id)` rows with
different `created_at`, the head pointer is no longer a unique row reference.

The holder's H3 "cross-partition resolution" test is therefore under-specified:
it proves the writer can append across partitions, but it does not prove the
database still has one row identity for the value the head stores.

### 3. Dropping the chain-head FK leaves a runtime-DML hole

The holder says Go/SD co-transactionality replaces the dropped FK. That only
covers the enumerated application writers. It does not cover the table's current
SQL privilege surface.

Source grants the runtime role direct `SELECT, INSERT, UPDATE` on
`repo_event_chain_heads` (`go/pkg/db/sql/0006_events_chain_anchors.sql:106-112`),
and the write-authority inventory explicitly classifies the table as
`ClassRuntimeDML`, not SD-gated (`go/pkg/db/write_authority_inventory.go:50-55,
115`). Today, the SQL FK is the DB guard that prevents this table from pointing
at a non-existent event. Once the FK is dropped and no replacement trigger/check
is added, this direct runtime-DML statement becomes valid:

```sql
UPDATE striatumd.repo_event_chain_heads
   SET last_event_id = 999999999999,
       last_hash = 'not-an-event-row-hash',
       updated_at = now()
 WHERE repository_id = 'repo_1';
```

With the current FK, commit fails unless `events(repo_1, 999999999999)` exists.
Under the holder's reshape, the FK is gone and the row can fork the chain head
from the event table. A grep/AST guard over Go writer sites does not catch this,
because the failure is no longer a Go writer-site problem; it is a database
privilege and constraint problem.

## Strongest rebuttal

The strongest defense is that all legitimate append paths call `nextval`, insert
the event/audit row, compute hashes from the prior head, and update the head in a
single transaction. Under that model, duplicate event ids require a bad
out-of-band insert or sequence/copy bug, duplicate audit hashes require a SHA-256
collision or bad owner/backfill insert, and the chain-head direct-update example
is not a normal daemon code path.

That defense lowers the guarantee. RFC 0136 is specifically about preserving
existing constraints while reshaping owner-held append-only chained tables. The
current guarantees are database-enforced. The proposed replacement relies on a
closed application writer set while leaving at least one relevant table
runtime-writable and while changing the key shape so the old FK cannot even name
the parent row. If the intended outcome is "we accept losing these DB
constraints," the holder must say that honestly and the core claim must stop
saying every existing integrity guarantee is preserved. If the intended outcome
is preservation, the build needs a compensating in-DB mechanism.

## Required repair

Before this clears, the SPEC needs one coherent database-level replacement for
the guarantees it removes:

1. Preserve global `audit_log.row_hash` uniqueness outside the partitioned
   unique index, for example with an unpartitioned `audit_row_hashes(row_hash
   PRIMARY KEY, audit_id, ts)` registry populated atomically by `append_audit_row`
   and by the owner backfill, or a deferred constraint trigger that rejects an
   existing `row_hash` anywhere in the partition tree under an explicit lock.
2. Preserve `events(repository_id,event_id)` row identity outside the partitioned
   PK, for example with an unpartitioned `event_identities(repository_id,
   event_id, created_at, PRIMARY KEY (repository_id, event_id))` registry
   populated before the partitioned insert/backfill, or another documented
   in-DB guard that makes duplicate logical event ids impossible.
3. Either keep a real chain-head FK by adding `last_created_at` to
   `repo_event_chain_heads` and referencing
   `events(repository_id,event_id,created_at)`, or revoke direct runtime
   `INSERT/UPDATE` on `repo_event_chain_heads` and replace it with an SD function
   or trigger that verifies the target event row under lock. A writer-set guard
   must include SQL privileges, not only Go call sites.
4. Add pgtests for all three failing cases above: duplicate audit `row_hash`
   across partitions rejected; duplicate `(repository_id,event_id)` across
   partitions rejected; direct runtime-DML head advance to a non-existent event
   rejected after the SQL FK is removed.

## Verdict

Real gap remains. H1 correctly identifies the forced PostgreSQL reshape, but H3
does not supply an equivalent guard for the narrow uniqueness and FK guarantees
the reshape removes. The gate should not clear until the SPEC either adds those
database-level replacements or explicitly narrows the promise and accepts the
loss of SQL-enforced row identity, global audit hash uniqueness, and chain-head
referential integrity.
